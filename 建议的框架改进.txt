  JFrame 框架改进建议
  （来源：编写 jframe_example 示例插件时的发现）
  注：建议 5、6 已落地修复（详见各建议的「修复情况」），其余仍为可选优化。

除已标注「✅ 已修复」的建议 5、6 外，其余均为「可选优化」。按优先级排列：


--------------------------------------------------------------------------------
建议 1（高）：JFrameMain 构造器 private → protected
--------------------------------------------------------------------------------

【现状】
文件：jframe_main/src/main/java/io/github/JiangHu/jframe/main/JFrameMain.java

    public class JFrameMain extends PluginBase {
        ...
        private JFrameMain() {                              // ← private
            this.applicationContext = new AnnotationConfigApplicationContext(SpringConfig.class);
        }
        ...
        private void bindPlugin() { ... }                   // ← private
    }

【问题】
JFrameMain 封装了一套完整的「Spring 引导 + 模块动态加载 + PluginAware 绑定」逻辑，
但构造器与 bindPlugin() 均为 private，导致业务插件无法继承它来复用这套逻辑。
示例中的 ExamplePlugin 不得不把 bindPlugin() 整段复制一遍（见 ExamplePlugin.bindPlugin）。

【建议】
将构造器改为 protected，bindPlugin() 改为 protected：

    protected JFrameMain() { ... }
    protected void bindPlugin() { ... }

这样业务插件可以：
    public class MyPlugin extends JFrameMain {
        @Override
        public void onEnable() {
            satisfyRequired(ConfigEnum.EVENT, ConfigEnum.FORM, ConfigEnum.THREAD);
            // 直接复用父类的容器与绑定逻辑
        }
    }

【影响范围】仅可见性放宽，不改变任何运行时行为，向后兼容。


--------------------------------------------------------------------------------
建议 2（中）：FormView 增加 goBack() 方法
--------------------------------------------------------------------------------

【现状】
文件：jframe_form/src/main/java/io/github/JiangHu/jframe/form/FormView.java

目前视图导航只有两个方法：
    addStack(FormView)   —— 压入子界面（进入下一级）
    replaceThis(FormView)—— 弹出当前并压入新界面（同层替换）

缺少「返回上一级」的语义：仅弹出当前视图，显示栈中上一个界面。
当前实现「返回」必须 replaceThis(重新构造上一个视图)，既冗余又可能丢失状态。

【背景】
SinglePlayerViewManager.send() 在 onClicked 回调后会自动重新发送栈顶界面，
因此「弹出当前视图」后，上一个界面会被自动刷新显示，无需额外处理。

【建议】
在 FormView 中增加：

    /**
     * 返回上一级界面（弹出当前视图，显示栈中上一个界面）。
     * 若当前已是栈底，则不做任何操作。
     */
    public void goBack() {
        if (manager.getViews().size() > 1) {
            manager.pop();
        }
    }

【收益】
示例 StatsView 的「返回主菜单」按钮可从
    replaceThis(new MainMenuView(threadService, player));
简化为
    goBack();
无需重新构造主菜单视图，且能保留主菜单的原始状态。


--------------------------------------------------------------------------------
建议 3（中）：ViewService 在玩家退出时自动清理
--------------------------------------------------------------------------------

【现状】
文件：jframe_form/src/main/java/io/github/JiangHu/jframe/form/ViewService.java

ViewService 为每位打开过界面的玩家创建一个 SinglePlayerViewManager，
并保存在 managers 映射表中。但玩家退出游戏时没有任何自动清理逻辑，
需要业务插件自行监听 PlayerQuitEvent 并调用 viewService.remove(player)，
否则会造成 Player 对象与视图栈的内存泄漏。

【建议】
方案 A（框架侧自动清理）：让 ViewService 监听 PlayerQuitEvent（需 Plugin 实例，
可让 ViewService 实现 PluginAware），在玩家退出时自动 remove(player)。

方案 B（文档侧）：在 ViewService 的 Javadoc 中明确提示
「需在 PlayerQuitEvent 中调用 remove(player)」，并在示例中补充该监听。

【当前示例的处理】
示例 ExamplePlugin 暂未注册 quit 清理（为保持示例聚焦于核心演示），
若长期运行建议补上：
    @EventHandler
    public void onQuit(PlayerQuitEvent e) {
        viewService.remove(e.getPlayer());
    }

建议 4（高 / 已在示例中规避）：Spring 在 Nukkit 插件中找不到 classpath 资源
--------------------------------------------------------------------------------

【现象】
示例插件首次在真实 Nukkit 服务器运行时报：
    java.io.FileNotFoundException:
    class path resource [thread-spring.xml] cannot be opened because it does not exist
尽管 thread-spring.xml 实际存在于 fat jar 根目录。

【根因】
各模块 SpringConfig 使用 @ImportResource("classpath:xxx-spring.xml")。
Spring 解析 classpath: 资源时，DefaultResourceLoader 使用
ClassUtils.getDefaultClassLoader()，其优先级为：
    1) Thread.currentThread().getContextClassLoader()   ← Nukkit 主线程的是服务器类加载器
    2) Spring 自身所在类的类加载器
Nukkit 主线程的上下文类加载器是「服务器类加载器」，它看不到插件 jar 内部资源，
因此即使资源在 jar 里也找不到。

【影响】
框架自带的 JFrameMain 作为插件运行时会触发完全相同的问题
（它在 onEnable/构造器里直接 new AnnotationConfigApplicationContext(...)）。
这是一个框架级缺陷，不只是示例的问题。

【建议（框架侧）】
在 JFrameMain 创建上下文处，临时切换线程上下文类加载器为插件类加载器：

    ClassLoader prev = Thread.currentThread().getContextClassLoader();
    Thread.currentThread().setContextClassLoader(getClass().getClassLoader());
    try {
        this.applicationContext = new AnnotationConfigApplicationContext(SpringConfig.class);
    } finally {
        Thread.currentThread().setContextClassLoader(prev);
    }

【当前示例的处理】
ExamplePlugin.onEnable 已采用上述方式规避（见该方法的注释），
因此示例可正常运行，无需等待框架修复。

建议 5（高 / ✅ 已由框架作者修复）：各模块 SpringConfig 类名冲突，导致 Bean 互相覆盖
--------------------------------------------------------------------------------

【现象】
示例插件在真实 Nukkit 服务器运行时报：
    NoSuchBeanDefinitionException: No bean named 'eventService' available
尽管 Spring 容器 refresh 成功、event-spring.xml 也加载了。
通过诊断程序打印容器内全部 Bean 名，发现：
    beans = [..., springConfig, threadService]
即四个模块的业务 Bean（eventService / viewService 等）全部丢失，只剩最后一个
模块（thread）的 Bean。

【根因】
core / event / form / thread 四个模块各自的配置类都叫 SpringConfig：
    jframe_core   ...core/config/SpringConfig.java
    jframe_event  ...event/config/SpringConfig.java
    jframe_form   ...form/config/SpringConfig.java
    jframe_thread ...thread/config/SpringConfig.java
Spring 的 AnnotationBeanNameGenerator 默认用「简单类名」生成 Bean 名
（首字母小写），因此这四个配置类生成的 Bean 名全部是 springConfig。
当它们被放进同一个 ApplicationContext 时，后注册的覆盖先注册的，
最终只有「最后一个」配置类的 @ComponentScan / @ImportResource 生效，
其余模块的业务 Bean 全部丢失。

【影响】
这是框架级缺陷：只要业务插件把多个模块的 SpringConfig 放进同一个容器
（这正是 JFrameMain 的设计意图），就会触发该问题。

【建议（框架侧）】
任选其一：
  A) 给每个模块的配置类取不同的类名，例如：
       EventSpringConfig / FormSpringConfig / ThreadSpringConfig / CoreSpringConfig
  B) 保持类名不变，但在 @Configuration 上显式指定不同的 Bean 名：
       @Configuration("eventSpringConfig")

【框架修复情况】
✅ 框架作者已采纳方案 A，将各模块配置类重命名为：
    CoreSpringConfig / EventSpringConfig / FormSpringConfig / ThreadSpringConfig / MainSpringConfig
并同步更新了 MainSpringConfig 的 @Import 与 ConfigEnum 的引用。
现在多个模块的配置类可安全共存于同一 ApplicationContext，Bean 名不再冲突。

【当前示例的处理】
ExamplePlugin 仍直接用 ClassPathXmlApplicationContext 加载各模块的 *-spring.xml
（XML 中每个 Bean 都有显式 id，与配置类无关），因此无论框架是否修复均不受影响。

建议 6（高 / ✅ 已修复）：event-spring.xml 存在构造器循环依赖
--------------------------------------------------------------------------------

【现象】
若直接用 Spring 加载 event-spring.xml，容器启动即抛：
    BeanCurrentlyInCreationException: Error creating bean with name 'handlerRegistry':
    Requested bean is currently in creation: Is there an unresolvable circular reference?

【根因】
event-spring.xml 中两个 Bean 互相引用，且注入方式形成「构造器 ↔ setter」循环：

    <bean id="eventService" class="...EventService">
        <property name="handlerRegistry" ref="handlerRegistry"/>   ← setter 注入
    </bean>
    <bean id="handlerRegistry" class="...HandlerRegistry">
        <constructor-arg ref="eventService"/>                      ← 构造器注入
    </bean>

对应源码：
  - HandlerRegistry 持有 final EventService eventService（必须构造器注入）；
  - EventService 持有非 final HandlerRegistry handlerRegistry（setter 注入）。

Spring 无法解析「构造器注入」参与的循环依赖（构造器注入不能被代理/延迟），
因此加载失败。

【影响】
框架级缺陷：任何通过 Spring XML 加载 event 模块的代码都会触发。

【当时给出的候选方案】
  A) 将 HandlerRegistry 的 eventService 由 final + 构造器注入，改为 setter 注入
     （去掉 final，提供 setEventService），使双方都走 setter，Spring 即可解析；
  B) 在其中一方的注入点加 @Lazy；
  C) 重构两者关系，消除互相依赖（拆分出独立组件，形成单向 DAG）。

【框架修复情况】
✅ 已采纳方案 C 的变体：将原 EventService 拆分为「内部引擎 + 公开门面」两层。

  原结构（循环）：
    EventService ←（构造器）→ HandlerRegistry

  新结构（单向 DAG，无环）：
    新增 EventEngine（内部 Nukkit 桥接引擎：subscribe/dispatch/bindPlugin，无任何依赖）
        ↑
    HandlerRegistry（构造器依赖 EventEngine，不再依赖 EventService）
        ↑
    EventService（公开门面：构造器依赖 HandlerRegistry + EventEngine，
                  register/unregister/evict 委托前者，subscribe 转发给后者）

  Spring 创建顺序：EventEngine → HandlerRegistry → EventService，三者均为构造器注入，
  不再存在循环依赖，event-spring.xml 可被 Spring 直接加载。

  涉及文件：
    - 新增 jframe_event/.../event/EventEngine.java
    - 重写 jframe_event/.../event/EventService.java（改为轻量门面）
    - 修改 jframe_event/.../event/routing/HandlerRegistry.java（依赖改为 EventEngine）
    - 修改 jframe_event/.../resources/event-spring.xml（三 Bean 单向装配）

【当前示例的处理】
ExamplePlugin 现已通过 Spring 直接加载 event-spring.xml 获取 eventService Bean，
不再需要手动构造。三个模块（event/form/thread）统一由 ClassPathXmlApplicationContext 装配。
